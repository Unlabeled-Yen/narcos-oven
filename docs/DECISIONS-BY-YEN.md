# Yen 的設計決策記錄

_這裡是 Yen（AI 導入 builder）對系統架構做的 judgment call、不是雇主直接答的問題。_
_每一條都寫「Why」讓未來 Claude Code 讀到就懂為何這樣定。_

---

## 2026-07-02: 連續匯入場景的處理原則

**背景**：甜點店 24 hr 接單、賣貨便會隨時被雇主重新匯出並丟進系統。這種連續匯入場景下會遇到 5 種情境（新單/付款完成/舊單消失/資訊變動/重複匯入）。原本 spec 只處理付款完成（R2-2），沒設計「消失」和「變動」——這是重大漏洞。

### D-1. 消失訂單一律進「消失待確認」桶、雇主逐一拍板

**選項比較**：
- ✅ **選：全部進桶、逐一分類**（最安全、辛苦但可控）
- ❌ 預設「已出貨」+ 雇主可覆蓋（風險：漏改）
- ❌ 靜默視為完成（風險：客訴、烤錯數量）

**Why**: 賣貨便匯出的訂單「消失」有三種可能語意（已出貨/已取消/雇主匯錯），系統沒有 signal 可以自動判斷。憲章原則 1「靜默失效機率 = 0%」要求任何無法自動判定的都必須由人拍板。

**How to apply**:
- 憲章新增 **#9 訂單消失守恆律**
- Stage 6c 每筆 disappeared 訂單 status → `disappeared_pending_resolution`
- 消失桶未清空前，Excel/PDF 產出 disabled
- UX 設計：鍵盤快速分類 (1=已出貨 / 2=已取消 / 3=暫留)

---

### D-2. 取消訂單若「已印過標籤」→ 問雇主能不能重印

**Why**: 
- 印過標籤代表出爐排程已下、包貨師可能已經 pull 該單
- 自動作廢會讓包貨師看到「多印一張沒用的標籤」——實務上不清晰
- 但雇主拍板可以重印同批其他單、避免整批重印

**How to apply**:
- Order.`frozen_after_label_print: boolean` 欄位
- 若消失單被雇主標為「已取消」且 frozen=true → UI 詢問：
  - [同批其他單重印] （較常用、只影響那張作廢的位置）
  - [整批重印]（少用、整批標籤重來）
  - [不重印] （包貨師手動識別作廢）

---

### D-3. 資訊變動一律進「變動待確認」桶、絕不 auto-overwrite

**Why**: 
- 憲章原則 1 的直接推論：客人改單如果被系統靜默採納，可能發生「烤了 A 品項但標籤上是 B」的實務事故
- 雇主必須在中間看到 diff（原本 X → 現在 Y）
- 尤其對已排入批次的訂單、變動必須經人為判斷是否重排

**How to apply**:
- 憲章新增 **#10 資訊變動守恆律**
- 關鍵欄位定義：`c12`(品項)、`c22`(配送數量)、`c17`(運費)、`c18-c20`(折抵)、`c21`(總額)、`c11`(收件門市)
- 任一關鍵欄位變動 → status = `change_pending_resolution`
- UX 顯示 diff view（before vs after 雙欄）
- 三選項：[接受變動]（重跑 pipeline）/ [保留舊資料]（拒絕客人修改）/ [拒絕變動要求]（需要跟客人溝通）

---

### D-4. M3 採「完整重導 SQLite 資料模型 + diff 邏輯」一起做（4-5 hr）

**Why**: 
- 匯入 diff 邏輯需要 SQLite 才能比對 db_active vs new_ids
- 分兩階段做（先 UX 再 diff）風險是「累積一堆資料後 diff 邏輯上線要手動遷移」
- 一次做完雖然時程長、但一上線就完整可用

**替代方案評估**（為什麼不選）:
- M3.5 先做基本待處理桶 UX → 使用中已累積資料 → M3.5 補 diff 時要手動 migrate。太痛
- 跳到 M4 先做 Excel 產出 → 等於強迫雇主先手動保護到 diff 上線。違反憲章

**How to apply**:
- 資料模型調整先做（M3.2）
- persistence 層用 Dexie.js IndexedDB（M7 遷 SQLite 純 backend）
- diff engine 實作（M3.3）
- UX 匯入異動摘要頁（M3.4）
- verify script 模擬「兩次匯入」測試（M3.5）

**時程更新**: 原本 M3 待處理桶 2 hr → 現在 M3 完整重導約 4-5 hr。M4 Excel 產出等 M3 完成。

## 2026-07-02（下午）: 排程系統定位（M6 藍圖）

**背景**: Yen 洞察「不論客人有沒有指定、最終都是雇主排出貨日」。原本 spec 把客人指定的 batchDate 當作最終出爐日、系統把它當已決定值。實際上雇主是所有訂單的最終排程者、客人指定只是**建議**。

### D-5. batchDate demoted 為建議、assigned_batch_date 才是最終真相

**Why**: 
- 客人選 7/7、雇主可能改到 7/14（因為 7/7 超載）
- 客人沒選、雇主一定要排
- 統計上「7/7 出爐 120 顆」的來源必須是**雇主拍板的 assigned_batch_date**、不能是客人建議

**How to apply**:
- Order 資料模型加 3 個欄位：customer_wish_date / system_suggested_date / assigned_batch_date
- 加 assignment_source 記錄「這日期怎麼來的」
- Excel/PDF/標籤產出只認 assigned_batch_date
- 憲章新增 **#11 排程雇主拍板守恆律**
- 相關：[[narcos-oven-constitution]]

---

### D-6. 排程規則預設「下次週二」

**Why**: 
- 從歷史資料觀察 6/09 6/16 6/23 7/07 7/14 全是週二 → NARCOS.sugar 常規出爐日是週二
- 這是最少改動的規則、雇主接手後可調
- 若雇主給不同 rule、改 config 一格就好

**How to apply**:
- Stage 8 排程建議引擎、customer_wish_date 為 null 時 → 下一個週二
- 若下週二該 atom 已超載（Stage 9）→ 建議下下週二
- 雇主可在 config UI 改成「下次週三」或「訂購日+N」等

---

### D-7. 產能上限預設值（雇主未提供前）

**Why**: 
- 若不預設、Stage 9 產能檢核無法運作、所有訂單都能自動排入
- 預設值需要足夠寬鬆（避免雇主一直看到「超載」警告）、但也要能捕捉異常爆量
- 從資料觀察 6/23 出爐 135 顆肉桂捲、7/07 預計 120 顆 → 200 是合理上限

**預設值**:
- 肉桂捲: 200 / 天
- 蘋果肉桂捲: 200 / 天
- 巴斯克類（全）: 50 / 天
- 香料堅果醬: 100 / 天
- 磅蛋糕類: 30 / 天

**How to apply**:
- menu.yaml 新增 production_capacity 段
- UI 顯示「⚠️ 這是估值、請設實際值」直到雇主明確 confirm
- 憲章 **#12 產能超載守恆律**：超載絕不 auto-assign

---

### D-8. Milestone 順序：M4 → M5 → M6 → M7

**Why**: 
- M4 (Excel) 是雇主 minimum viable output——即使沒排程系統、能匯出 Excel 就能給主廚/行銷看
- M5 (標籤) 是最緊急的實體產出——沒標籤不能出貨
- M6 (排程) 是真正的核心系統、但需要雇主先看到 M4/M5 才知道要什麼
- M7 (儀表板 + MCP) 是「已經有排程資料之後才有意義」

**替代方案評估**:
- 先做 M6 排程再做 M4 Excel：問題是雇主不能拿到任何實體產出、動工很久才看到成果
- 跳過 M4 直接 M5：Excel 是最需要給合作方（主廚/行銷）看的、不能跳
- M4 + M6 同步：M4 需要 assigned_batch_date、M6 才產這個值——所以 M4 v1 用 batchDate (現有欄位) 先產出、M6 上線後 M4 升級用 assigned_batch_date

**How to apply**:
- 立刻進 M4：以現有 batchDate 為出爐日產 Excel
- M4 產出的 Excel 標明「這些是客人建議/系統抓的日期、非雇主拍板」
- M5 標籤同理
- M6 完成後、M4/M5 升級用 assigned_batch_date
