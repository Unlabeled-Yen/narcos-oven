_這裡是 Yen（AI 導入 builder）對系統架構做的 judgment call、不是雇主直接答的問題。_
_每一條都寫「Why」讓未來 Claude Code 讀到就懂為何這樣定。_

## 2026-07-02: 連續匯入場景的處理原則

**背景**：甜點店 24 hr 接單、賣貨便會隨時被雇主重新匯出並丟進系統。這種連續匯入場景下會遇到 5 種情境（新單/付款完成/舊單消失/資訊變動/重複匯入）。原本 spec 只處理付款完成（R2-2），沒設計「消失」和「變動」——這是重大漏洞。

### D-1. 消失訂單一律進「消失待確認」桶、雇主逐一拍板

**選項比較**：
- ✅ **選：全部進桶、逐一分類**（最安全、辛苦但可控）
- ❌ 預設「已出貨」+ 雇主可覆蓋（風險：漏改）
- ❌ 靜默視為完成（風險：客訴、烤錯數量）

**Why**: 賣貨便匯出的訂單「消失」有三種可能語意（已出貨/已取消/雇主匯錯），系統沒有 signal 可以自動判斷。憲章原則 1「靜默失效機率 = 0%」要求任何無法自動判定的都必須由人拍板。

**How to apply**:
- 憲章新增 **#9 訂單消失守恆律**
- Stage 6c 每筆 disappeared 訂單 status → `disappeared_pending_resolution`
- 消失桶未清空前，Excel/PDF 產出 disabled
- UX 設計：鍵盤快速分類 (1=已出貨 / 2=已取消 / 3=暫留)

---

### D-2. 取消訂單若「已印過標籤」→ 問雇主能不能重印

**Why**: 
- 印過標籤代表出爐排程已下、包貨師可能已經 pull 該單
- 自動作廢會讓包貨師看到「多印一張沒用的標籤」——實務上不清晰
- 但雇主拍板可以重印同批其他單、避免整批重印

**How to apply**:
- Order.`frozen_after_label_print: boolean` 欄位
- 若消失單被雇主標為「已取消」且 frozen=true → UI 詢問：
  - [同批其他單重印] （較常用、只影響那張作廢的位置）
  - [整批重印]（少用、整批標籤重來）
  - [不重印] （包貨師手動識別作廢）

---

### D-3. 資訊變動一律進「變動待確認」桶、絕不 auto-overwrite

**Why**: 
- 憲章原則 1 的直接推論：客人改單如果被系統靜默採納，可能發生「烤了 A 品項但標籤上是 B」的實務事故
- 雇主必須在中間看到 diff（原本 X → 現在 Y）
- 尤其對已排入批次的訂單、變動必須經人為判斷是否重排

**How to apply**:
- 憲章新增 **#10 資訊變動守恆律**
- 關鍵欄位定義：`c12`(品項)、`c22`(配送數量)、`c17`(運費)、`c18-c20`(折抵)、`c21`(總額)、`c11`(收件門市)
- 任一關鍵欄位變動 → status = `change_pending_resolution`
- UX 顯示 diff view（before vs after 雙欄）
- 三選項：[接受變動]（重跑 pipeline）/ [保留舊資料]（拒絕客人修改）/ [拒絕變動要求]（需要跟客人溝通）

---

### D-4. M3 採「完整重導 SQLite 資料模型 + diff 邏輯」一起做（4-5 hr）

**Why**: 
- 匯入 diff 邏輯需要 SQLite 才能比對 db_active vs new_ids
- 分兩階段做（先 UX 再 diff）風險是「累積一堆資料後 diff 邏輯上線要手動遷移」
- 一次做完雖然時程長、但一上線就完整可用

**替代方案評估**（為什麼不選）:
- M3.5 先做基本待處理桶 UX → 使用中已累積資料 → M3.5 補 diff 時要手動 migrate。太痛
- 跳到 M4 先做 Excel 產出 → 等於強迫雇主先手動保護到 diff 上線。違反憲章

**How to apply**:
- 資料模型調整先做（M3.2）
- persistence 層用 Dexie.js IndexedDB（M7 遷 SQLite 純 backend）
- diff engine 實作（M3.3）
- UX 匯入異動摘要頁（M3.4）
- verify script 模擬「兩次匯入」測試（M3.5）

**時程更新**: 原本 M3 待處理桶 2 hr → 現在 M3 完整重導約 4-5 hr。M4 Excel 產出等 M3 完成。
